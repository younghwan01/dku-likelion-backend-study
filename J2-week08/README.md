# J2-week08 - REST API CRUD와 아이디/비밀번호 인증

## 학습 개요

이번 주에는 **Spring Boot 챕터 09(09-01 ~ 09-15)** 강의를 바탕으로 SURL 데이터를 REST API 형태로 생성·조회·수정·삭제하는 방법과, 사용자 인증 및 권한 확인의 필요성을 학습했다.

- **학습 목표:** CRUD API의 동작, DTO 사용, 인증(Authentication)과 인가(Authorization)의 차이 이해
- **진행 방식:** 제공된 강의 내용을 중심으로 개념과 처리 흐름 정리
- **학습 범위:** 09-01 ~ 09-15
- **실습 여부:** 이번 정리는 강의 요약 기반의 **이론 학습 기록**이다. 아래 요청 및 코드는 구조를 이해하기 위한 예시이며, 실제 서버 실행이나 Postman 테스트를 완료했다고 의미하지 않는다.

## 1. REST API로 SURL CRUD 구현 (09-02 ~ 09-03, 09-06 ~ 09-08)

기존 URL 단축 서비스(SURL)의 기능을 REST API 형태로 바꾸면서 자원 중심으로 URL을 구성하는 방법을 배웠다. 하나의 자원에 대해 HTTP 메서드로 작업을 구분한다.

| HTTP 메서드 | 기능 | API 예시 |
| --- | --- | --- |
| `POST` | SURL 생성 | `POST /api/v1/surls` |
| `GET` | 단일 SURL 조회 | `GET /api/v1/surls/1` |
| `GET` | SURL 목록 조회 | `GET /api/v1/surls` |
| `PUT` | SURL 수정 | `PUT /api/v1/surls/1` |
| `DELETE` | SURL 삭제 | `DELETE /api/v1/surls/1` |

클래스에는 `@RestController`, `@RequestMapping("/api/v1/surls")`를 지정하고, 기능별로 `@PostMapping`, `@GetMapping`, `@PutMapping`, `@DeleteMapping`을 사용할 수 있다.

- **생성:** 요청 Body에서 필요한 값을 받고, `@Valid`와 `@NotBlank` 등으로 유효성을 검사한 뒤 저장한다.
- **단일 조회:** `@PathVariable`로 URL의 ID를 받아 `findById()`로 찾고, 없으면 예외 처리한다.
- **목록 조회:** `findByOrderByIdDesc()` 같은 메서드로 최신 순 정렬 후 리스트를 반환한다. 데이터가 많으면 페이지네이션을 고려한다.
- **수정:** 수정할 ID로 데이터를 찾고 값을 변경한다. 강의에서는 `PUT`을 사용했다. 일부 필드만 수정할 때는 `PATCH`도 사용할 수 있다.
- **삭제:** 삭제 대상이 있는지 확인한 뒤 삭제하고, 필요한 경우 삭제 결과를 응답한다.

예를 들어 SURL을 생성하는 요청은 다음처럼 만들 수 있다. **아래는 설명을 위한 예시 요청**이다.

```http
POST /api/v1/surls
Content-Type: application/json

{
  "body": "검색사이트",
  "url": "https://example.com"
}
```

## 2. DTO로 응답에 포함할 데이터 관리 (09-04)

엔티티를 API 응답으로 그대로 반환하면 DB 내부 구조가 노출되거나, 회원 정보 같은 불필요한 값이 함께 전달될 수 있다. 강의에서는 `@JsonIgnore`로 특정 필드를 가리는 방법과 **DTO(Data Transfer Object)**로 응답에 필요한 값만 선택하는 방법을 다뤘다.

```java
// 개념을 설명하기 위한 DTO 예시
public record SurlResponse(
    Long id,
    String body,
    String url
) {}
```

DTO를 사용하면 응답 형식을 명확히 하고, 엔티티 구조를 바꾸더라도 외부 API에 미치는 영향을 줄일 수 있다. 특히 비밀번호와 같은 민감한 정보는 응답 DTO에 넣지 않아야 한다.

목록 조회 시에는 엔티티 리스트를 Stream으로 변환할 수 있다.

```java
// 개념 예시: surls는 조회한 엔티티 리스트
var items = surls.stream()
    .map(surl -> new SurlResponse(surl.getId(), surl.getBody(), surl.getUrl()))
    .toList();
```

## 3. HTTP 요청 처리와 DB 커넥션 (09-05)

클라이언트가 HTTP 요청을 보내면 서블릿 컨테이너는 요청과 응답을 처리하기 위한 `HttpServletRequest`와 `HttpServletResponse`를 제공한다.

```text
클라이언트 → HTTP 요청 → 서블릿 컨테이너 / Spring MVC
           → Controller → Service → Repository → DB
           ← HTTP 응답 (상태 코드, 헤더, Body)
```

- `HttpServletRequest`: 요청 경로, 헤더, 파라미터, 본문 등 요청 정보에 접근
- `HttpServletResponse`: 응답 상태, 헤더, 본문 등을 구성
- **DBCP(Connection Pool):** DB 연결을 매번 새로 만드는 비용을 줄이기 위해 연결을 재사용하는 방식
- **트랜잭션:** 여러 DB 작업을 하나의 작업 단위로 묶으며, 수정·삭제에는 적절한 쓰기 트랜잭션이 필요

강의에서 나온 **OSIV(Open Session in View)**는 요청을 처리하는 동안 영속성 컨텍스트를 열어 둘 수 있는 설정이다. OSIV가 켜졌다고 DB 커넥션을 반드시 요청 종료까지 점유하는 것은 아니다. 일반적으로 트랜잭션 경계는 Controller보다 **Service 계층**에 두는 편이다.

## 4. 인증과 인가의 차이 (09-09 ~ 09-10, 09-14)

이전 단계에서는 로그인 사용자 대신 특정 회원을 임의로 지정해 처리했다. 하지만 실제 서비스에서는 요청자가 누구인지 확인해야 하고, 확인된 사용자가 해당 데이터에 접근할 권한이 있는지도 검사해야 한다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| **인증(Authentication)** | 요청자가 누구인지 확인 | ID/비밀번호가 맞는지 확인 |
| **인가(Authorization)** | 요청자가 이 작업을 해도 되는지 확인 | 내 SURL만 수정·삭제 가능 |

예를 들어 회원 A가 올바른 ID와 비밀번호를 입력하면 **인증**에는 성공할 수 있지만, 회원 B의 SURL을 삭제하려는 요청은 **인가** 단계에서 거부되어야 한다.

강의에서는 현재 작업을 수행하는 사용자를 **actor(액터)**라고 부르고, 이 사용자와 SURL 작성자의 ID를 비교하는 권한 체크를 설명했다.

```java
// 개념 예시: actor와 surl이 null이 아닐 때 작성자 ID 비교
boolean canModify(Member actor, Surl surl) {
    if (actor == null || surl == null) return false;
    return actor.getId().equals(surl.getAuthor().getId());
}
```

조회·수정·삭제마다 동일한 비교를 반복하기보다 별도의 인증·권한 서비스에 공통 로직을 분리하면 유지보수에 도움이 된다. 다만 작업 종류에 따라 권한 규칙은 달라질 수 있다.

## 5. HTTP의 무상태성과 인증 정보 전달 (09-11 ~ 09-13)

HTTP는 기본적으로 **무상태(Stateless)** 방식이므로 각 요청은 독립적으로 처리된다. 사용자가 요청에 `userId=1`이라고 적는 것만으로 실제 1번 회원임이 증명되지는 않는다.

강의에서는 URL 파라미터, HTTP 헤더, 요청 Body를 통해 사용자 정보를 전달하는 방식을 비교하고, ID만 보내는 방식에는 한계가 있으므로 비밀번호 검증이 필요하다고 설명했다.

ID/비밀번호 인증의 기본 흐름은 다음과 같다.

```text
ID / 비밀번호 입력
   ↓
서버에서 아이디에 해당하는 회원 조회
   ↓
저장된 비밀번호 해시와 입력 비밀번호 비교
   ↓
인증 성공 또는 실패
   ↓
인증된 사용자의 대상 데이터 접근 권한 확인
   ↓
작업 수행 또는 거부
```

실제 서비스에서는 비밀번호를 평문으로 저장하지 않고 **BCrypt 등 적절한 해시 알고리즘**으로 검증해야 한다. 또한 매 요청마다 비밀번호를 전달하는 방식 대신 로그인 후 **세션 또는 토큰**을 이용하는 방법이 일반적이다. 인증 정보는 HTTPS로 안전하게 전송해야 한다.

일반적으로 인증 정보가 없거나 유효하지 않으면 HTTP **401**, 인증에는 성공했지만 작업 권한이 없으면 **403**으로 구분한다. 구체적인 응답은 서비스 설계에 따라 달라질 수 있다.

## 6. Request Scope와 요청 내 캐싱 (09-13, 09-15)

여러 Controller에서 현재 회원을 가져오는 로직을 반복하면 코드가 길어지므로, 요청 단위로 사용하는 객체(`Rq` 등)에 공통 기능을 모을 수 있다.

같은 요청 중 `getMember()`를 여러 번 호출할 때마다 DB를 조회하면 불필요한 비용이 발생한다. 처음 한 번 조회한 회원을 **요청 범위**에서 보관하고 이후에는 그 값을 다시 사용하는 방법을 학습했다.

```text
첫 번째 getMember() → DB 조회 → 요청별 변수에 저장
두 번째 getMember() → 저장된 값 반환
세 번째 getMember() → 저장된 값 반환
```

이때 캐시가 **사용자별·요청별로 분리**되는 것이 중요하다. 여러 요청이 공유하는 싱글톤 서비스 필드에 로그인 회원을 저장하면 다른 사용자의 데이터와 섞일 수 있다.

## 정리 및 느낀 점

이번 챕터를 통해 CRUD API를 작성하는 것에서 한 단계 더 나아가, **누가 요청했는지 확인하고 권한이 있는 작업만 처리하는 것**이 중요하다는 점을 이해했다. 특히 인증과 인가는 비슷해 보였지만, 로그인에 성공한 사용자도 다른 사람의 데이터를 마음대로 수정하거나 삭제할 수는 없다는 차이가 명확해졌다.

또한 DTO는 필요한 데이터만 반환하는 역할을 하고, Request Scope와 요청 내 캐싱은 중복 코드를 줄이면서 불필요한 DB 조회를 줄이는 데 도움이 된다는 점을 정리했다. 이후에는 로그인 기능을 실제로 구현하고, 정상 요청과 인증 실패 및 권한 부족 상황을 각각 테스트해 보고 싶다.
